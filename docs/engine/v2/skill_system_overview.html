Sistema de Skills — visão de adoção

Adoção integral do schema v2 maximalista ao código atual. Este documento parte do schema como verdade e descreve o caminho de migração.

1. Princípio

O sistema de skills passa a seguir o schema v2 integralmente: vocabulário coeso inspirado em L2off (skilldata.txt), com catálogos pequenos, prefixos por eixo, e campos ortogonais em vez de strings monolíticas.

Duas separações independentes acontecem juntas:

  1. Regra ↔ Apresentação. A regra (trigger, alvo, custo, efeito) vive no core. A copy (name, label, text) vive em arquivo de locale por idioma.
  2. Formato ↔ Conteúdo. O arquivo de regra muda de JSON para YAML para permitir comentários, reduzir ruído de sintaxe e dar legibilidade a skills com 5+ effects compostos.
Memória do projeto: Core é a fonte da verdade — UI consome regras do core; nunca duplicar lógica de jogo na UI. A separação regra/copy reforça esse princípio. Efeito repetido vira primitiva DSL no core; script só para lógica única. O catálogo do v2 explicita o que é primitiva e o que sobra para script.

3. As 7 dimensões do schema v2

3.1 Apresentação separada + arquivo em YAML

Templates (name, labelTemplate, textTemplate) saem do arquivo de regra. skills.json vira skills.yaml. Copy mora em skills.locale.pt-BR.yaml.

skills.yaml (regra)

- id: skill_last_light_healing
  name: { pt: Cura da Última Luz, en: Last Light Healing }
  operate_type: op_active
  nature: [nat_magical, nat_holy]
  target_type: tgt_target
  affect_scope: scp_single
  affect_object: obj_friend
  affect_limit: { min: 1, max: 1 }
  cost: { mp: 2 }
  cooldown: { scope: combat, charges: 1 }
  effects:
    - kind: i_heal
      to: $target
      amount: [3, 3, 5, 5, 8]

skills.locale.pt-BR.yaml (copy)

skill_last_light_healing:
  label: "Cura da Última Luz ({amount}): ..."
  text: cure {amount} de vida de um herói
        ou criatura aliada.

O campo name com i18n inline ({ pt, en }) também pode migrar inteiro para o locale; o doc v2 deixa essa decisão aberta. Adotamos a versão mais limpa: todo texto humano vai para locale, o YAML de regra fica só com identificadores.

3.2 operate_type — como a skill executa

ValorSignificado
op_activeAtiva instantânea (player ativa, resolve uma vez).
op_active_buffAtiva com duração (player ativa, efeito persiste).
op_triggeredReage a evento; exige trigger.event.
op_passivePassiva permanente (enquanto a fonte estiver em jogo).

Substitui a inferência implícita do trigger: string atual. "Quando a skill dispara" deixa de estar escondido no nome do trigger e vira campo de primeira classe.

3.3 trigger.event (evt_*) + conditions[] + cooldown estruturado

As ~64 trigger strings compostas (once_per_room_after_roll, combat_if_dungeon_red_or_purple) colapsam em 18 eventos atômicos + condições + cooldown como campos próprios.

Antes

trigger: once_per_room_after_roll

Depois

operate_type: op_triggered
trigger:
  event: evt_roll
cooldown:
  scope: room
  charges: 1

Catálogo evt_* (18 eventos):

GrupoEventos
Combateevt_attack_declared, evt_roll, evt_hit, evt_damage_dealt, evt_damage_taken, evt_destroy, evt_kill
Cicloevt_combat_start/end, evt_round_start/end
Sala / dungeonevt_room_reveal, evt_room_enter, evt_room_leave, evt_dungeon_discard
Entidadeevt_enter_play, evt_leave_play, evt_targeted

conditions[] combinadas com AND; any_of para OR:

conditions:
  - { kind: awakening, gte: orange }
  - { kind: in_combat }
  - { kind: owner_hp_pct, lte: 50 }
  - any_of:
      - { kind: target_has_status, status: bleeding }
      - { kind: target_has_status, status: poisoned }

cooldown com scope: game/room/combat/round e charges: N. Cooldown ausente = sem limite.

3.4 Targeting de 4 eixos

O target: string monolítico (hero_or_ally_creature, creatures_or_heroes_in_room, blue_die_and_self...) é decomposto em 4 eixos ortogonais. A perspectiva "amigo/inimigo" deixa de estar hardcoded no nome — o motor resolve pela posição do caster.

EixoValoresSignificado
target_typetgt_self/target/enemy/item/others/noneQuem você seleciona.
affect_scopescp_single/party_full/dead_party/room/noneO que o efeito atinge a partir do alvo.
affect_objectobj_friend/not_friend/allFiltro aliado/inimigo (relativo ao caster).
affect_limit{ min, max }Quantidade. {0,0} ou omitido = sem limite.

3.5 nature[]

Lista cumulativa de categorias que a skill carrega — uma skill pode ser nat_magical + nat_holy simultaneamente, e cruzar com resistências da criatura em ambos os eixos.

GrupoValores
Tiponat_physical, nat_magical
Elementosnat_fire, nat_water, nat_earth, nat_wind, nat_holy, nat_dark
Estadosnat_bleed, nat_poison, nat_shock, nat_paralyze, nat_sleep, nat_hold, nat_derangement
Especiaisnat_death, nat_true

Hoje entra como campo declarativo. O sistema de resistências por nature (redução/imunidade nas criaturas) é o passo seguinte e fica fora do escopo do patch-21 — entra quando o design de combate exigir.

3.6 cost estruturado

Substitui o defaultValue ad-hoc por campos nominais:

cost:
  hp: 0
  mp: 2
  discard: 0

Campos com valor 0 podem ser omitidos. Catálogo extensível conforme o jogo evoluir.

3.7 Arrays-por-cor + null-skip

Este é o eixo que mata o slash-pair de vez. Dois mecanismos coordenados, ambos em resolveExpr:

Arrays-por-cor em qualquer valor de effect. Qualquer valor numérico aceita escalar ou array de 5 posições indexado por state.despertar (white, yellow, orange, red, purple):

effects:
  - kind: i_heal
    to: $target
    amount: [3, 3, 5, 5, 8]    # escala por despertar
  - kind: i_damage
    to: $target
    amount: 5                   # vale em qualquer despertar

Null-skip. Posição null no array = aquele effect não dispara naquele despertar. Substitui requiresAwakening e dispensa um bloco levels[]:

effects:
  - kind: i_heal
    to: $target
    amount: [3, 3, 5, 5, 8]
  - kind: i_dispel
    to: $target
    category: poison
    amount: [null, null, null, null, 1]   # só dispara em purple

Múltiplos valores independentes vão inline. Quando a skill tem 2+ valores distintos, cada um mora no value/amount do seu próprio effect — o stat já nomeia o que é. Sem campo intermediário:

effects:
  - kind: p_modifier
    to: $self
    stat: s_damage_reduction
    value: [3, 3, 4, 4, 5]
    duration: { kind: while_in_play }
  - kind: p_modifier
    to: $self
    stat: s_purple_damage_reduction
    value: [2, 2, 2, 3, 3]
    duration: { kind: while_in_play }

Override por carta continua via $value escalar — o mecanismo atual ([useSkill.ts](src/core/skills/useSkill.ts)) preserva como está. cardRef.params.value alimenta $value; arrays-por-cor moram inline no effect, não em campo separado.

O doc maximalista descreve um params: nomeado para agregar valores; descartamos esse nível de indireção. Inline com stat nomeando cada valor é mais direto, e nenhum caso real do jogo precisa de override-por-carta de múltiplos valores independentes. params entra na pauta quando aparecer skill que precise.

3.8 Prefixos de catálogo (i_/p_/t_/c_/s_/op_/nat_/tgt_/scp_/obj_/evt_)

Todo valor de catálogo carrega prefixo curto indicando de qual eixo vem. grep i_ lista todo o catálogo de instantâneos; um valor solto nunca se confunde com outro catálogo.

nat_nature[]nat_magical, nat_holy
tgt_ / scp_ / obj_Targetingtgt_target, scp_room, obj_friend
evt_trigger.eventevt_roll, evt_damage_taken
i_kind instantâneoi_damage, i_heal
p_kind persistentep_modifier, p_status
t_kind tick no alvot_damage (DoT), t_heal (HoT)
c_kind tick no casterc_damage, c_resource

Stats fora do catálogo s_* viram erro de compile — mata stat fantasma (declarado no YAML mas não lido pelo motor).

4. O que não muda

  • Pipeline DSL → stack → resolver → ECS: as 4 camadas continuam. add_modifier deixa de fazer dual-write quando combat legacy for aposentado (continuidade do patch-18 Lote G — patch próprio).
  • Triggers reativos via p_trigger (antigo add_trigger): já é declarativo; só ganha catálogo evt_*.
  • Effect stack ordenado via event_rules.json LIFO/FIFO: segue.
  • Override por carta via cardRef.params: já funciona, segue. Arrays-por-cor não tiram esse mecanismo — a carta pode sobrescrever um array inteiro.
  • Scripts como escape hatch: continuam para padrões que não se repetem.

5. Scripts — escape hatch, não substituto

O catálogo de primitivas do v2 cobre quase tudo. Para padrões que não se repetem, mantemos script.

Critério unificador

O schema v2 entra inteiro porque suas dimensões se reforçam: operate_type + trigger.event + cooldown + conditions só faz sentido se os 4 vierem juntos; targeting de 4 eixos só vale se substituir o target string monolítico em todas as skills; prefixos só pagam grep-ability se cobrirem o catálogo inteiro. Adoção parcial cria dois dialetos coexistindo, com o pior dos dois mundos.

O que adiamos não é "metade do schema" — é extensão futura do mesmo vocabulário (resistências consomem nature[]; charges são novas primitivas alinhadas com i_/p_; DoT/HoT preenchem os prefixos t_/c_).
