Arquitetura — Motor de Card Game

Engine headless com multi-front e canal de IA

Camadas

Camada de dados

Definição estática do conteúdo do jogo. Cartas, skills e keywords vivem em JSON; cartas com efeitos complexos referenciam scripts externos. O engine só interpreta — nada de lógica hardcoded.

Engine core (headless)

Núcleo autoritativo do jogo, sem nenhuma dependência de UI. Reúne o rules engine (valida ações legais), o effect resolver (executa efeitos com triggers, stack e ECS), o game state (verdade autoritativa com RNG determinístico baseado em seed), o event bus interno (pub-sub entre sistemas) e o event log append-only (fonte da verdade pra replay, snapshot e reconexão).

Projection layer (Fog of War)

Filtra o estado e os eventos por perspectiva antes de sair do engine. Jogador A vê só a própria mão, espectador vê tudo aberto, IA recebe a view do jogador que assiste ou view completa se for analista. Toda regra de visibilidade vive aqui.

Transport layer

Abstrai o protocolo de comunicação. Mesma mensagem com encoders diferentes: WebSocket pros fronts humanos, MCP pra IA, canal estilo DAP pra ferramentas de debug. Trocar ou adicionar protocolo não toca o engine.

Consumidores

Clientes externos do engine. Fronts humanos (web, mobile, desktop, espectadores), canal de IA (LLMs via MCP pra jogar, analisar ou treinar bots) e ferramentas de dev (inspector, balanceador, replay viewer). Todos consomem o mesmo event stream — só diferem em projeção e permissão.

Princípios que amarram tudo

Direção única de fluxo

Comandos sobem (cliente → transporte → rules → engine), eventos descem (engine → log → projeção → transporte → cliente). Nunca o contrário.

O event log é a verdade

Estado atual é projeção dos eventos, não o contrário. Replay, time-travel, reconexão e simulação what-if pela IA saem de graça.

Projeção é onde mora a segurança

Toda regra de quem pode ver o quê vive numa camada só. Adicionar modos novos (deck público, espectador delayed) muda só a projeção.
