1. O que é um script nesse contexto

Um script é um pequeno arquivo de código (Lua, JavaScript ou similar) que descreve o comportamento de uma carta específica quando o JSON declarativo não consegue expressá-lo. É a extensão programável do sistema de cartas, plugada em pontos específicos do engine.

Conceitualmente, é o mesmo papel dos arquivos .nasc do Lineage 2 Off — código de comportamento que vive fora do engine compilado e é interpretado em runtime. A diferença é que aqui ele é integrado a um sistema declarativo mais amplo: 85-90% das cartas são puro JSON, e o script entra só onde a lógica passa do limite do declarativo.

O script não substitui o JSON. Ele é referenciado de dentro do JSON, em campos específicos, e o engine sabe interpretar o ponteiro.

{
  "id": "necromancer_supreme",
  "cost": 5,
  "attack": 3,
  "health": 4,
  "effects": [
    {
      "trigger": "on_friendly_minion_death",
      "action": { "type": "script", "ref": "necromancer_supreme.on_death" }
    }
  ]
}

Acima, tudo é JSON estático exceto a ação — que delega pra um arquivo de script. O engine resolve normalmente até bater no "type": "script" e, nesse ponto, chama o interpretador.

2. Que tipo de "dado" é um script

Essa é a parte sutil: um script não é dado, e não é código do engine — é uma terceira categoria. Vale entender as três:

Dado puro (JSON)

Declarativo. Descreve o que é. Não tem lógica executável. Editado por designer. Validado por schema. Versionado como conteúdo.

Código do engine

Imperativo, compilado. Define como o jogo funciona. Implementa as regras universais. Editado por programador. Versionado como software.

Script — categoria intermediária

Imperativo, interpretado, conteúdo (não software). Define o comportamento específico de uma carta. Usa uma API restrita do engine. Editado por designer técnico ou programador de gameplay. Versionado junto com as cartas, não com o engine.

É código executável, mas é tratado como asset do jogo. Designers podem editar sem compilar o engine. Pode ser recarregado em runtime. Vive na pasta de conteúdo, não na pasta de código-fonte.

3. Por que implementar

O sistema de scripts existe pra resolver um problema concreto que aparece cedo no desenvolvimento de qualquer card game sério. Os motivos, em ordem de impacto:

3.1 Expressividade — JSON puro quebra rápido

JSON é ótimo pra descrever, péssimo pra expressar lógica. Tenta colocar isso em JSON puro:

"Olhe as últimas 3 cartas jogadas esse turno. Se forem de tipos diferentes, copie uma delas aleatoriamente, mas se alguma custar mais de 5 mana, transforme essa carta numa cópia gratuita até o fim do próximo turno."

Dá pra fazer — vira um JSON aninhado de 80 linhas com condicionais e referências cruzadas. Ninguém lê, ninguém debuga, nenhuma exceção pode ser adicionada sem quebrar tudo. Regra empírica: se um efeito tem mais de 2 condicionais ou precisa "olhar pra trás" no estado, ele quer ser script.

3.2 Velocidade de iteração — hot reload muda o jogo

Sem scripts, qualquer ajuste em comportamento de carta exige: alterar código, recompilar engine, reiniciar servidor, recarregar partida. Ciclo: minutos.

Com scripts: editar arquivo, salvar, próximo trigger da carta usa o código novo. Ciclo: segundos. Ao longo de meses de desenvolvimento isso representa multiplicação de produtividade, não economia marginal.

3.3 Separação de responsabilidades

Programador de engine deixa de ser gargalo pra criação de cartas. Designer técnico edita comportamento sem tocar no código do engine. Reduz risco — bug em script de carta não derruba engine inteiro, só falha aquela carta.

3.4 Permite cartas que seriam impossíveis

Mecânicas como "Discover" (Hearthstone), "level-up de campeão" (Legends of Runeterra), bosses de PvE com AI customizada — essas só existem porque há um sistema de script. Sem ele, o teto de complexidade do jogo fica limitado ao que o engine antecipou.

3.5 Modabilidade e extensibilidade

Se você quiser permitir que a comunidade crie cartas, modos custom, ou expansões não-oficiais — scripts viabilizam isso de forma controlada. Sandbox impede que mods comprometam o servidor.

O custo de não implementar: ou você limita o design das cartas ao que o JSON suporta (jogo fica raso mecanicamente), ou você adiciona lógica especial direto no engine pra cada carta complexa (engine vira espaguete em 6 meses).

4. Arquitetura do subsistema

O sistema de scripts vive dentro do effect resolver — não é um sistema paralelo. Ele adiciona 4-6 componentes novos ao engine, todos dentro da mesma fronteira:

Componentes em detalhe

Dispatcher

Decide, pra cada efeito do JSON, se executa via handler nativo ou via script. É um if/else dentro do resolver, não um sistema à parte.

Script Runner

O interpretador embarcado (Lua VM, QuickJS, etc). Geralmente uma instância por partida, com contextos isolados. Recebe um handler já compilado e o invoca.

Script Registry

Carrega arquivos da pasta scripts/, compila uma vez, mantém em cache indexado por nome. Responde "me dá o handler necromancer.on_play".

Context Builder

Antes de invocar o script, monta o objeto ctx com variáveis (self, controller, event) e a API exposta. É a "ponte" entre script e engine.

API Bindings

Conjunto de funções do engine expostas ao script: deal_damage, draw, summon, prompt_target, random. É o vocabulário que o script tem disponível.

Hot Reload Watcher

File watcher na pasta scripts/. Quando arquivo muda, invalida o cache do Registry. Próxima invocação relê do disco. Opcional, mas multiplica produtividade.

6. A API exposta ao script

O script não acessa o estado diretamente. Ele só pode usar as funções que o engine expõe via o objeto ctx. Isso é fundamental por três motivos: segurança, evolução do engine (mudar interno sem quebrar scripts) e debugabilidade.

Exemplo de script usando a API

-- scripts/necromancer_supreme.lua

function on_death(ctx)
  -- Conta minions amigos que morreram esse turno
  local deaths = ctx.count_deaths_this_turn({
    controller = ctx.self.controller
  })

  if deaths >= 3 then
    -- Summona um boss
    ctx.summon("skeleton_lord", { side = "own_board" })
  else
    -- Summona um esqueleto normal
    ctx.summon("skeleton", { side = "own_board" })
  end
end

7. Sandbox e determinismo

O sandbox é tão importante quanto a API exposta. Scripts vão ser editados por designers, recarregados em runtime, potencialmente vindos de mods. Não pode ser vetor de problema.

O que o script NÃO pode fazer

  • Acessar filesystem (io.open, require arbitrário)
  • Acessar rede ou sockets
  • Executar comandos de OS, ler variáveis de ambiente
  • Fazer reflection profunda no host
  • Usar RNG próprio — sempre ctx.random
  • Loops infinitos — há limite de instruções por execução
  • Alocar memória sem limite — quota por script
  • Acessar estado de outras partidas (isolamento por sessão)

Determinismo — armadilha sutil

A arquitetura inteira depende de determinismo (replay, simulação de IA, reconexão). Scripts podem quebrar isso facilmente sem perceber:

  • RNG: nunca math.random() da linguagem; sempre ctx.random()
  • Tempo real: nada de os.time() ou Date.now() — use turno/fase
  • Ordem de iteração: ao iterar hash maps, garantir ordem estável
  • Estado externo: sem variáveis globais persistentes — estado vive no game state

O sandbox deve impedir mecanicamente essas violações: remove math.random, os.time e similares do environment antes de carregar scripts. Designer não consegue errar — a função simplesmente não existe.

8. Decisões de implementação

Cinco decisões concretas que esse subsistema força. Tomar essas com clareza desde o início economiza retrabalho depois.

Qual linguagem de script

Recomendação: Lua como default. Footprint mínimo, embedding trivial, sandboxing bem entendido, é padrão da indústria de jogos. Alternativa razoável: TypeScript via QuickJS se a stack inteira é Node. Outras opções têm trade-offs piores.

Quais pontos do JSON aceitam script

Decidir explicitamente em quais slots o script pode entrar: action, condition, target, value, ou carta inteira. Não deixar implícito — schema do JSON deve validar.

Qual a API exposta

Lista fechada e versionada de funções ctx.*. Começa pequena (10-20 funções), cresce conforme demanda. Cada função nova é decisão consciente, não acidente.

Limites do sandbox

O que está bloqueado: filesystem, rede, OS, RNG próprio, tempo real, globals persistentes. Limites de execução: máximo de instruções, máximo de memória, timeout.

Hot reload sim ou não

Recomendação: sim, desde o dia 1. O ganho de produtividade é grande demais pra deixar pra depois. Implementação é simples (file watcher + cache invalidation).

Resumo em uma linha: o sistema de scripts é uma extensão programável do JSON declarativo, plugada em pontos específicos do effect resolver via dispatcher, permitindo expressar cartas que JSON puro não consegue, sem inflar o engine com lógica especial — ao custo de implementar 4-6 componentes no resolver e definir um sandbox claro.
