Estudo de migração — Lineage 2 Off para stack moderna

Do skilldata.txt monolítico ao engine headless com ECS, event log e multi-cliente

1. O ponto de partida vs o ponto de chegada

O que muda essencialmente

Hoje, o conteúdo (skilldata.txt) e o motor (l2server.exe) andam juntos: o servidor lê o arquivo, mas a lógica de cada efeito está hardcoded no binário. Editar uma skill significa ajustar parâmetros declarativos, mas qualquer mecânica nova exige patchar bytecode.

A arquitetura alvo separa de forma estrita conteúdo, motor, log e transporte. Cada camada tem uma única responsabilidade e pode ser substituída isoladamente. O client L2 original continua suportado por um adapter de protocolo, e novos consumidores (web, mobile, bots de IA) entram sem tocar o motor.

2. Camadas do engine alvo

Content layer

O skilldata.txt vira um conjunto de arquivos YAML/JSON versionados em git, validados por JSON Schema. Skills, keywords, traits e o catálogo de primitivas de efeito ficam separados em pastas, com i18n nativo e diff legível em PR.

Engine core

Headless, sem dependência de UI ou rede. Reúne o rules engine (valida ações legais), o effect resolver (executa primitivas declaradas no conteúdo), o ECS world (entidades, componentes, sistemas) e o event log (fonte da verdade para replay e reconexão). RNG determinístico com seed garante que o mesmo input produz o mesmo output.

Projection layer

Filtra estado e eventos por perspectiva antes de sair do engine. Player vê HP exato próprio e percentual dos outros, espectador vê tudo aberto, IA recebe a view do jogador que assiste ou view completa se for analista. Toda regra de visibilidade vive aqui.

Transport layer

Abstrai o protocolo. Mesma mensagem com encoders diferentes: adapter binário para o client L2 original (preserva base de jogadores), WebSocket para web/mobile, MCP para IA, gRPC para ferramentas internas. Trocar ou adicionar protocolo não toca o engine.

3. ECS — por que faz sentido para o L2

OOP (hoje no L2OFF)

class CPlayer : public CPlayable {
  int hp, mp, cp;
  Position pos;
  vector<Abnormal*> abnormals;
  Inventory inv;
  // ... +200 campos
  void TakeDamage(int dmg);
  void ApplyBuff(...);
  // ... +500 métodos
}

ECS (alvo)

// Componentes: dados puros
Health    { current, max }
Position  { x, y, z }
Bleeding  { power, tick, exp }
Casting   { skillId, t0, target }

// Sistema = função sobre query
BleedTickSystem(now) {
  for e in [Bleeding, Health] {
    if now >= e.Bleeding.nextTick {
      e.Health.current -= power
      ...
    }
  }
}

Abnormals viram componentes

O abnormal_type do skilldata.txt é literalmente um componente. Stun, bleed, poison, hold, root, haste — cada um vira um componente que aparece ou some da entidade. A regra de stacking por abnormal_lv vira uma função de três linhas em vez de varredura de lista em CCreature.

Player, NPC, pet, summon — sem hierarquia de classes

A pergunta if target->IsPlayer() else if target->IsNpc() desaparece. Um sistema de dano só precisa saber se a entidade tem Health. Cubic, decoy, trap, torre de siege — tudo é entidade com combinação de componentes. Adicionar um tipo novo é só decidir quais componentes ele carrega.

Determinismo e replay sai de graça

Sistemas iteram em ordem fixa sobre componentes em layout fixo. Snapshot é serializar componentes; restaurar é ler de volta. Replay aplica o event log sobre snapshot zero. O L2 original usa rand() global e tem ponteiros pendurados entre objetos — replay perfeito é impossível. Em ECS com seed é trivial.

4. Como uma skill é representada nos dois mundos

Hoje — uma linha do skilldata.txt (Backstab)

skill_begin  skill_name=[s_backstab1]  skill_id=30  level=1
  operate_type=A1  magic_level=38
  effect={{i_backstab;1107;300;2000};{i_death2;4;1}}
  operate_cond={{equip_weapon;{dagger}}}
  is_magic=0  mp_consume2=60
  cast_range=40  effective_range=400
  skill_hit_time=1.08  skill_cool_time=0.72  reuse_delay=11
  attribute=attr_death  effect_point=-305
  target_type=enemy  affect_scope=single
skill_end

O efeito i_backstab;1107;300;2000 é uma caixa-preta. Os três números encapsulam dano, bônus por estar atrás, possível bleed embutido e provavelmente uma condição de crítico. Tudo vive hardcoded em CEffectBackstab dentro do .exe.

Alvo — YAML declarativo com primitivas explícitas

id: backstab
display_name:
  en: Backstab
  pt: Punhalada nas costas
levels:
  - level: 1
    magic_level: 38
    cast: { time: 1.08, cool: 0.72, reuse: 11 }
    resources: { mp: { cast: 60 } }
    range: { cast: 40, effective: 400 }
    targeting: { target: enemy, scope: single }
    conditions:
      - equip_weapon: [dagger]
      - position: behind
    effects:
      - type: physical_attack
        power: 1107
        crit_bonus: 300
      - type: apply_abnormal
        abnormal: bleed
        power: 50
        duration_ms: 2000
      - type: mark
        kind: death
        level: 1
    trait: death

O efeito monolítico explode em primitivas legíveis. O bleed vira apply_abnormal com tipo, poder e duração. A condição "estar atrás do alvo" — que hoje está escondida dentro de CEffectBackstab — fica explícita em conditions. Game designer ajusta números sem tocar código.

5. Caminho de migração — sem big bang

  1. Converter skilldata.txt em YAML validado

    Parser lê o .txt UTF-16 e cospe YAML com schema. Exportador faz o caminho de volta para o formato original enquanto o servidor antigo ainda roda. Ganho imediato: PRs revisáveis, validação, diff legível.

  2. Catalogar e desmontar os monolíticos

    Para cada efeito i_<nome_de_skill> hardcoded (Backstab, Fatal Blow, Mortal Blow…), descobrir por engenharia reversa de comportamento in-game o que ele encapsula, e remontar como composição de primitivas no YAML. O .txt exportado mantém compatibilidade.

  3. Engine novo headless em modo shadow

    Implementa o engine novo lendo o YAML. Não substitui produção: roda em paralelo recebendo os mesmos inputs e comparando outputs. Onde divergir, ou o YAML está errado ou o engine novo está. Itera até bater consistentemente.

  4. Event log e replay

    Engine novo passa a gravar event log append-only. Agora existem replays de partidas reais, antes mesmo do cutover. Permite análise retrospectiva, balance tooling, e replays para os players.

  5. Projection + transport novos

    Camadas de projeção e transporte por cima do engine novo. Adapter binário mantém o client L2 original funcionando; client web entra como segundo consumidor; canal MCP abre para bots de IA.

  6. Cutover gradual

    Quando o shadow passa X semanas sem divergência, vira o tráfego. O .exe velho fica como fallback por mais um tempo e é desligado depois.

6. Riscos conhecidos

Os monolíticos escondem regras sutis

i_backstab provavelmente tem uma lógica de "atrás = X%, lado = Y%, frente = falha" que não está documentada em lugar nenhum. A engenharia reversa por comportamento in-game é tediosa e propensa a erro. Reservar tempo de QA específico para isso.

RNG não-determinístico no original

O L2 original usa rand() global do servidor. Replay perfeito requer reimplementar fórmulas com PRNG seeded, e isso pode dar resultados ligeiramente diferentes dos canônicos. Decidir cedo entre fidelidade absoluta e determinismo — geralmente determinismo ganha, e os players não percebem.

Abnormal stacking é cheio de exceções

abnormal_type + abnormal_lv é a regra geral, mas tem casos especiais hardcoded — "Dance de X não conflita com Song de Y mesmo com mesmo type", buffs de set de armadura, etc. Precisa de uma tabela explícita de exceções na content layer.

O client original limita o que dá para inovar

Skill nova com efeito que o client legado não conhece não renderiza direito (ícone errado, animação ausente). Manter compatibilidade com o client original é uma jaula útil até o client web pegar tração.
