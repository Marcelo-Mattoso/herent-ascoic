1. Ponto de partida

O documento script_architecture.html descreve o subsistema de forma genérica — pensado para um engine de card game qualquer, possivelmente com servidor, possivelmente recebendo mods de terceiros. Aqui adaptamos esse modelo ao contexto específico deste projeto:

  • Aplicação standalone no front (Vite + React 19 + TypeScript)
  • Sem backend — o engine roda no navegador do jogador
  • Single-player solo, sem usuários não confiáveis
  • Já existe um effect resolver com registry de handlers em src/core/skills/handlers/
  • Persistência via localStorage; replay e event log já implementados

O resultado: várias preocupações do doc original somem ou ficam triviais, e o subsistema fica muito mais barato de implementar — porque vira essencialmente uma extensão tipada do registry de handlers que já está no código.

2. A fronteira data-driven

A premissa central desse subsistema: o engine é data-driven. Existem duas pastas com naturezas diferentes, e a separação é explícita:

🛠 src/core/ — o motor

Código do engine. Reducer, sistemas, event bus, resolver, registry. Programador edita. Mudar aqui é mudar como o jogo funciona.

🎨 src/data/ — o conteúdo

O que o jogo é. Cartas, skills, balance, transições, e scripts. Designer edita. Mudar aqui é mudar o que existe no jogo, não como o jogo funciona.

O ponto fundamental: scripts vivem em src/data/, não em src/core/. Eles são conteúdo, igual ao JSON — só que conteúdo executável. Designer mexe nos dois lados (JSON e script) sem nunca abrir o core.

Por que essa separação importa

  • Quem edita o quê fica óbvio. Tudo dentro de src/data/ é jogo de design. Tudo fora é engine.
  • Revisão segue caminhos diferentes. PR que toca só src/data/ é revisão de design — balanceamento, fluxo de carta. PR que toca src/core/ é revisão de engenharia — invariantes, performance, determinismo.
  • O engine não conhece nenhuma carta específica. Se você ler todos os arquivos de src/core/, não acha string "necromancer_supreme" em lugar nenhum. O engine é genérico; só src/data/ sabe das cartas.
  • Adicionar carta nova é mexer em uma pasta só. JSON da carta + (se exótica) script da carta, ambos em src/data/. Sem tocar no core.

Regra prática: se você precisa abrir src/core/ pra adicionar uma carta, é sinal de que falta uma primitiva no engine — não de que a carta é especial demais. A primitiva genérica entra no core uma vez; cartas específicas viram dados em src/data/.

Layout da pasta de entrada

src/data/                       # tudo que o designer edita
├── cards.json                  # catálogo declarativo de cartas
├── skills.json                 # catálogo de skills
├── balance.json                # parâmetros de balance
├── transitions.json            # transições de estado
├── event_rules.json            # regras de evento
└── scripts/                    # comportamentos exóticos por carta
    ├── necromancer_supreme.ts
    ├── reliquia_do_caos.ts
    └── ...

Tudo em uma pasta. Designer abre src/data/ e tem o jogo inteiro do ponto de vista de conteúdo — declarativo (JSON) ou imperativo (TS). O core nunca aparece.

Nota sobre o estado atual: hoje src/data/scripts/ abriga scripts avulsos de desenvolvimento (executáveis via npm run script). Antes de adotar a proposta, esses precisam migrar pra outro lugar (sugestão: tools/dev-scripts/ ou src/dev-scripts/), liberando src/data/scripts/ pro seu papel real — scripts de carta carregados pelo engine.

3. O que muda no contexto web

Preocupação do doc genérico No contexto deste projeto
Sandbox forte contra mods maliciosos some Não há código de terceiros. Scripts são parte do bundle, escritos pela mesma pessoa que escreve o engine.
Embedding de Lua/QuickJS some Não precisa. TS módulos já são "scripts" do ponto de vista do JSON declarativo.
Isolamento por sessão / múltiplas partidas some Uma sessão por aba. Estado global é a Elf store.
Hot reload grátis HMR do Vite resolve. Editou .ts, salvou, próxima invocação usa o novo.
File watcher para invalidar cache grátis Mesma resposta: Vite já faz.
API tipada para o script grátis Sai de graça com TypeScript — autocomplete, refactor seguro, erros de compilação.
Testes do script grátis Vitest já roda sobre TS — script é só um módulo a mais.
Determinismo (replay, IA) continua Você precisa garantir manualmente — sem Math.random, Date.now, ordem de iteração instável.
Expressividade além do JSON continua Esse é o motivo de existir. Vale o investimento.
Separação carta-vs-engine continua Quanto mais cartas exóticas, mais útil.

Resumo: sai todo o peso de "embarcar interpretador + montar sandbox". Sobra o que importa — um lugar bem definido pra colocar lógica de carta que não cabe em handler genérico.

4. O que já existe no engine

Boa parte da arquitetura do doc já está implementada — só não tem esse nome. Mapeamento direto:

Componente do doc Já existe como
Action Registry src/core/skills/registry.ts + handlers/index.ts (~35 handlers nativos)
Dispatcher src/core/effects/resolver.ts — lê type da skill e busca no registry
Effect Stack src/core/effects/stack.ts
Event Bus src/core/events/ (DamageAboutToBeDealt, HealAboutToBeApplied, etc)
API Bindings (núcleo) src/core/systems/ — damageSystem, healSystem, conditionSystem
Hot Reload Watcher Vite HMR
Conteúdo declarativo (JSON) src/data/ (cards, skills, balance, transitions)

O que não existe ainda:

  • Um slot no JSON do tipo { "type": "script", "ref": "..." } que aponte para lógica ad-hoc por carta
  • Um ctx rico (hoje os handlers recebem value: number | string | null — escalar)
  • Um diretório src/core/scripts/cards/ separado dos handlers genéricos

Em outras palavras: você tem o registry e o dispatcher; falta o "modo carta exclusiva".

5. O gap real

Hoje, se aparecer uma carta com lógica peculiar — por exemplo, uma reação que olha o histórico de salas, conta inimigos derrotados em condições específicas, ou se ramifica em 3 sub-efeitos com condições diferentes — você tem duas opções ruins:

  1. Cria um handler novo que só essa carta usa. Polui o registry, e o contrato escalar (value: number | string | null) força gambiarras pra passar parâmetros estruturados.
  2. Espalha a lógica pelo reducer. Pior — vira if (cardName === "X") { ... } em lugares que deveriam ser genéricos. O engine vira espaguete.

O sistema de scripts existe pra resolver exatamente isso: dar um terceiro lugar onde lógica de carta única pode viver, isolada, sem inflar nem o registry de handlers nem o reducer.

6. Proposta — pasta de entrada do designer

Dois lados, papéis distintos

A proposta separa a infra (que o engine precisa) da entrada (que o designer escreve). São duas pastas com naturezas opostas:

🛠 src/core/scripts/ — encanamento

Registry, builder de contexto, tipos. Implementado uma vez, raramente muda. Programador.

🎨 src/data/scripts/ — conteúdo

Um arquivo por carta exótica. Cresce conforme cartas aparecem. Designer.

Layout completo

# Lado do engine — programador edita
src/core/scripts/
├── registry.ts        # carrega src/data/scripts/*.ts via import.meta.glob
├── context.ts         # monta o Ctx tipado a partir do GameState + SkillContext
└── types.ts           # type ScriptHandler = (ctx: Ctx) => GameState

# Lado do conteúdo — designer edita
src/data/
├── cards.json         # catálogo declarativo
├── skills.json
├── balance.json
├── transitions.json
├── event_rules.json
└── scripts/           # comportamentos exóticos
    ├── necromancer_supreme.ts
    ├── reliquia_do_caos.ts
    └── ...

Como uma carta exótica fica

1. Designer abre src/data/skills.json e adiciona a skill apontando para o script:

// src/data/skills.json (trecho)
{
  "id": "necromancer_supreme_on_death",
  "trigger": "on_friendly_hero_death",
  "effect": { "type": "script", "ref": "necromancer_supreme.onDeath" }
}

2. Designer cria o arquivo do script na mesma pasta de entrada:

// src/data/scripts/necromancer_supreme.ts
import type { ScriptHandler } from "@/core/scripts/types";

export const onDeath: ScriptHandler = (ctx) => {
  const deaths = ctx.query.countHeroDeathsThisRoom(ctx.self.controller);

  if (deaths >= 3) {
    return ctx.action.summon("skeleton_lord", { side: "own" });
  }
  return ctx.action.summon("skeleton", { side: "own" });
};

Pronto. Nenhuma linha de src/core/ foi tocada. A carta exótica entrou só mexendo em src/data/.

O registry (lado do engine)

// src/core/scripts/registry.ts
import type { ScriptHandler } from "./types";

// Glob aponta pra pasta do designer, não pra dentro do core.
const modules = import.meta.glob<Record<string, ScriptHandler>>(
  "/src/data/scripts/*.ts",
  { eager: true }
);

const cache = new Map<string, ScriptHandler>();
for (const [path, mod] of Object.entries(modules)) {
  const cardKey = path.match(/scripts\/(.+)\.ts$/)![1];
  for (const [exportName, fn] of Object.entries(mod)) {
    cache.set(`${cardKey}.${exportName}`, fn);
  }
}

export function getScript(ref: string): ScriptHandler | undefined {
  return cache.get(ref);
}

O registry é o único componente do core que conhece o caminho da pasta de conteúdo. É a ponte. import.meta.glob com eager: true faz o bundler embutir todos os scripts no build de produção e dar HMR no dev — sem file watcher manual.

Olhada pelo lado do designer: a pasta src/data/ é o jogo. Cartas, skills, balance e comportamentos exóticos estão todos ali — declarativos ou imperativos. O engine é uma caixa preta que lê essa pasta e roda. Adicionar carta = mexer numa pasta só.

7. Fluxo de execução

  1. Evento dispara no event bus (ex: HERO_DIED)
  2. Resolver encontra a skill inscrita, lê seu effect
  3. Dispatcher vê effect.type === "script" e chama getScript(effect.ref)
  4. Context Builder monta o Ctx a partir do GameState + SkillContext atuais
  5. Script roda como função TS normal — sem VM, sem boundary
  6. Script retorna novo GameState (igual a qualquer handler)
  7. Resolver segue o loop, novos eventos emitidos vão pelo mesmo bus

Do ponto de vista do resto do engine, script e handler são intercambiáveis. Action log, replay, projeções — tudo continua funcionando porque o que importa é a mutação do GameState, não quem fez.

8. API exposta ao script

Diferente do doc genérico (onde a API é uma ponte entre linguagens), aqui ela é um contrato de tipos. O ganho não é segurança — é disciplina e refatorabilidade. Quando o engine muda internamente, o TS quebra os scripts em compile time, não em runtime.

NamespaceExemplosImplementação
ctx.self id, cardName, controller, currentLife Entity da carta que disparou (snapshot)
ctx.event type, source, target, amount Evento que ativou o trigger
ctx.query getActiveHeroes(), countHeroDeathsThisRoom(), getCurrentRoom() Wrappers sobre o GameState — read-only
ctx.action dealDamage(), heal(), summon(), drawItem() Wrappers sobre src/core/systems/
ctx.random int(min, max), pick(list) RNG determinístico — usar o mesmo da engine, nunca Math.random
ctx.log info(msg), warn(msg) Escreve no eventLog — mesma cor/canal dos handlers

Boa prática: o Ctx é a única dependência que um script importa. Se um script faz import { algoDoCore } from "../../...", é red flag — ou esse "algo" vira parte do Ctx, ou o script está vazando abstração.

9. Determinismo no browser

O sandbox forte do doc não existe aqui — não tem como remover Math.random ou Date.now de TS em runtime. Determinismo vira convenção + revisão, não barreira mecânica.

Os riscos práticos:

  • RNG: proibido Math.random() em qualquer script. Sempre ctx.random, que usa o RNG seedado da partida.
  • Tempo: proibido Date.now() / performance.now(). Use turno, fase, sala atual.
  • Iteração: ao iterar Map/objetos, ordenar antes — não confiar em ordem de inserção em estruturas que cruzam fronteira.
  • Estado global: nenhum módulo de script pode ter variável de top-level que mude com o tempo. Estado vive no GameState.

Como fazer isso prático sem inventar runtime:

  • Regra de lint — proibir Math.random, Date.now, performance.now dentro de src/data/scripts/** via Biome.
  • Teste de replay — rodar uma partida, capturar action log, re-executar action log do zero, comparar estados finais. Já está semi-pronto graças ao replay viewer.
  • Revisão — script novo é PR pequeno, fácil de inspecionar.

10. Roadmap incremental

A proposta cabe em etapas pequenas, cada uma independente. Pode parar em qualquer uma sem deixar lixo.

Fase 0 — liberar a pasta

Mover os scripts avulsos de dev que hoje moram em src/data/scripts/ pra tools/dev-scripts/ (ou similar). Ajustar npm run script. A pasta src/data/scripts/ passa a ser exclusiva de scripts de carta.

Fase 1 — andaime

Cria src/core/scripts/ com registry.ts (apontando para src/data/scripts/*.ts), types.ts, context.ts mínimo (só self, event, log). Sem nenhum script de carta ainda.

Fase 2 — dispatcher

Adiciona suporte a { "type": "script", "ref": "..." } no resolver. Testa com uma carta dummy que só loga.

Fase 3 — primeira carta real

Migra uma carta que hoje tem lógica desconfortável (handler exclusivo ou if no reducer) para script. Valida que replay funciona.

Fase 4 — API rica

Conforme novas cartas vêm, expande ctx.query e ctx.action. Lista fechada — cada função nova é decisão consciente.

Fase 5 — lint determinístico

Regras Biome bloqueando Math.random, Date.now em src/data/scripts/**.

Fase 6 — teste de replay

Suite que reexecuta action logs salvos e compara estados — pega regressões de determinismo automaticamente.

Quando não vale a pena: se as próximas N cartas planejadas se expressam confortavelmente como handlers genéricos, não tem urgência. O sistema só rende quando aparece a primeira carta que não cabe — aí as fases 1–3 ficam em ~150 linhas.

Resumo em uma linha: o engine é data-driven — src/data/ é a pasta de entrada do designer, contendo tanto o JSON declarativo quanto os scripts TS executáveis das cartas exóticas; src/core/ não conhece nenhuma carta específica e apenas interpreta o que estiver em src/data/. Adicionar carta = mexer em uma pasta só.
