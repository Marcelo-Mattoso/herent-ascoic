Arquitetura Web — Motor de Card Game

Motor autoritativo no navegador · single-player standalone · data-driven, event-driven, component-based

Adaptação da arquitetura abstrata (motor headless multi-front com canal de IA) para o ambiente navegador standalone: tudo roda numa única página, sem servidor. O propósito desta arquitetura é direto — garantir que a contabilidade do jogo feche. Skills, items, conditions, tokens e modificadores se combinam em centenas de configurações; uma contabilidade correta sai de três escolhas estruturais que andam juntas: data-driven (toda regra é dado, não código espalhado), event-driven (efeitos reagem a eventos pelo barramento, não por chamadas diretas) e component-based (entidades são compostas por componentes plugáveis; sistemas processam queries sobre eles). As fronteiras que no documento abstrato separavam servidor e cliente viram aqui fronteiras de módulo, de thread e de aba.

Camadas

Content / Data layer

Definição estática do conteúdo: cartas, skills, keywords, conditions, components atômicos, transições de fase. Toda regra é dado. Uma carta nova é uma entrada de JSON com seus componentes e triggers declarados — não exige código novo no caso comum. O escape hatch para mecânicas que não cabem em dado puro é uma função TS registrada pelo nome, invocada como referência declarativa no JSON (scripting embarcado pelo registry). No navegador, o conteúdo viaja empacotado com a aplicação — não há servidor de conteúdo em runtime.

Engine core

Núcleo autoritativo do jogo, sem nenhuma dependência de interface, DOM ou APIs do navegador. Reúne seis subsistemas que respondem juntos a cada comando do jogador:

  • Rules engine — valida se o comando é legal na fase atual e nas condições atuais.
  • State machine — fases do jogo (exploração, combate, recompensa, etc.) e estados de carta (no deck, na mão, em jogo, no descarte) explícitos, com transições validadas. Estado inconsistente impossível por construção.
  • Effect resolver — recebe a intenção, consulta triggers, empilha efeitos encadeados (stack) e delega a aplicação aos sistemas. É onde mora a contabilidade.
  • ECS world — entities (heróis, inimigos, salas, items em jogo) são identificadores; o que cada uma tem e faz mora em componentes plugáveis (Health, Damage, Conditions, Modifiers, Triggers, Tokens, etc.). Sistemas processam queries sobre componentes — não há lógica de carta espalhada em handlers monolíticos.
  • Event bus interno — pub-sub síncrono dentro do core. Quando um sistema produz um evento (DamageDealt, EnemyDefeated, RoomEntered, TurnStarted), outros sistemas inscritos reagem em ordem determinística. É o que faz "quando algo morre, ganhe X" funcionar sem código de carta saber da existência de outras cartas.
  • Game state + Action log — o estado autoritativo é serializável e contém a seed do RNG e a fase corrente; o log append-only de actions é a fonte da verdade (Command Pattern). Estado é sempre a projeção do log sobre o estado inicial.

Por que esses três (data-driven + event-driven + ECS) andam juntos: dano envolve modificadores de múltiplas fontes simultâneas (skill ativa do herói, item equipado, condition do inimigo, token de área, aura de outra criatura). Um sistema de dano consulta todas as fontes via query antes de calcular. Eventos (DamageAboutToBeDealt) deixam outros sistemas modificarem o valor antes da aplicação. Dados declarativos descrevem quem reage a quê. A contabilidade fecha porque existe um único lugar onde cada tipo de cálculo acontece, e ele enxerga tudo de uma vez.

Projection layer

Filtra estado e eventos por perspectiva antes de sair do engine. A interface do jogador recebe a view dele; uma IA oponente recebe view limitada (sem ver mão do humano, sem prever RNG futuro); um replay viewer recebe view completa. Toda regra de visibilidade vive aqui — não espalhada pela interface.

Engine adapter (no lugar do transport layer)

No navegador não há rede entre engine e jogador — então a transport layer do diagrama abstrato colapsa em fronteira de processo. O adapter expõe um contrato único: comandos entram, projeção e eventos saem. A mesma forma serve pra três cenários sem que o resto da aplicação perceba: motor rodando junto da interface (mesma thread), motor rodando em thread separada (libera a UI de cálculos pesados, libera a IA pra pensar sem travar), ou duas abas observando a mesma partida (uma joga, outra espectadora). Trocar o substrato muda só o adapter.

Consumidores

Interface do jogador é o consumidor primário: renderiza a projeção e devolve comandos do humano. IA local é um consumidor paralelo opcional — bot oponente, assistente de jogada, gerador de dicas — que consome view limitada e devolve comandos como qualquer outro jogador. Ferramentas de dev (inspector de ações, replay viewer, balanceador, runner com seed fixa pra reproduzir bug) consomem view completa e leem direto do action log.

Persistência local

Camada lateral, ausente do diagrama abstrato (que assume servidor). No navegador é onde o "log é a verdade" se materializa offline. Dois usos complementares: snapshot do estado pra retomada instantânea ao reabrir a aba, e action log persistido como histórico completo da partida — base de replays, exportação de bug reports, biblioteca de partidas anteriores. O engine não conhece os detalhes; só sabe ler/gravar através de uma porta abstrata. Política: o log é a fonte primária; snapshot é otimização.

Princípios que amarram tudo

Toda regra é dado (Data-Driven)

Cartas, skills, keywords, conditions, transições de fase, custos, modificadores — tudo declarado em arquivos. Código TS só interpreta dado e implementa os sistemas. Uma carta nova é uma entrada de JSON com componentes e triggers; só vira código quando a mecânica é genuinamente nova. Adicionar mecânica = adicionar dado + (raramente) adicionar sistema.

Sistemas reagem a eventos, não chamam uns aos outros (Event-Driven)

Quando algo acontece no jogo, o sistema responsável emite um evento no barramento; quem se inscreveu reage. Skills com trigger "quando inimigo morre" se registram como ouvintes de EnemyDefeated — não há acoplamento entre quem dispara e quem responde. Eventos são síncronos e ordenados: a ordem de resolução é determinística e auditável; cascatas (evento A dispara efeito que emite evento B) resolvem pela stack.

Composição em vez de hierarquia (Component-Based)

Entidades (heróis, inimigos, salas, items em jogo) são identificadores; o que cada uma é e faz mora em componentes plugáveis. Buff adiciona componente, dispel remove. Conditions, items, tokens, modifiers, triggers são todos componentes com forma uniforme. Sistemas processam queries ("todas as entidades com componente Armor") em vez de switch sobre tipos. Adicionar capacidade = adicionar componente, não inflar o reducer.

Direção única de fluxo

Comandos sobem (consumidor → adapter → rules → effect resolver → sistemas), eventos descem (sistemas → event bus → log → projeção → adapter → consumidor). Nunca o contrário. A interface não muta o game state direto — emite intenções e observa o resultado.

O action log é a verdade — inclusive offline

Estado atual é projeção das ações sobre o estado inicial, não o contrário. Disso saem de graça: retomar partida ao reabrir a aba, exportar replay como JSON, anexar log + seed a bug report, navegar no tempo dentro do inspector, simular "e se eu tivesse jogado outra carta" sem perder a partida real.

Determinismo é feature, não detalhe

Todo RNG passa pelo state (seed inicial + contador). Mesma seed + mesma sequência de ações = mesmo resultado, no navegador do jogador, na thread de IA local, no runner de testes. Sem aleatoriedade implícita escondida dentro de sistema. Sem este princípio, replay e bug repro não funcionam.

Projeção é onde mora a segurança

Toda regra de quem pode ver o quê vive numa camada só. Num single-player isso parece overkill, mas é o que impede que uma IA oponente local "espie" a mão do jogador ou olhe à frente no RNG. Adicionar modos novos (espectador em outra aba, replay público, IA cega) muda só a projeção.

A fronteira de processo é o eixo de evolução

O que hoje é chamada direta de função pode virar amanhã troca de mensagens entre threads, e depois entre abas. Pra isso o contrato precisa ser como se já fosse serializado desde o início: comandos e estado puramente em dados, sem referências vivas, sem closures, sem objetos opacos. Custa pouco agora; paga muito quando o motor sai da thread principal.

O engine ignora o navegador

O core não sabe que está num navegador. Não conhece DOM, não conhece persistência, não conhece o adapter que o invoca. Tudo que é "navegador" entra como dependência injetada através de portas abstratas (persistência, relógio, fonte de aleatoriedade pra seed inicial). O mesmo engine roda igual sob um runner de testes ou sob a interface real.

Como a contabilidade fecha

Esta arquitetura existe pra resolver um problema específico: a contabilidade de combinações entre skills, items, conditions, tokens e modifiers tem que fechar — sempre, em qualquer ordem, com qualquer combinação. Como cada padrão contribui:

Um cálculo, um sistema, uma query

Dano não é aplicado por uma skill nem por um item nem por uma condition — é aplicado pelo damage system, que recebe a intenção e enumera todas as fontes relevantes via query no ECS antes de calcular. Mesma ideia pra cura, draw, modificação de rolagem, etc. Não existe "ordem dos handlers" porque não existem handlers competindo — existe um sistema que vê tudo.

Eventos abrem janelas pra modificação

Antes de aplicar dano, o sistema emite DamageAboutToBeDealt no bus. Listeners inscritos (armor, damage_reduction, redirect) podem ajustar o valor ou cancelar. Depois da aplicação, emite DamageDealt; outros listeners reagem (on_damage_taken triggers, retaliação). A ordem dessas janelas é parte do contrato do evento, não acidente do código de carta.

Stack ordena cadeias

Efeito A dispara evento que aciona efeito B que dispara evento que aciona efeito C. Sem ordem clara, cada execução pode dar resultado diferente. A stack do effect resolver empilha efeitos pendentes e resolve em ordem definida (LIFO ou FIFO conforme a regra), com pontos de pausa explícitos pra escolha do jogador entre passos. Cadeia em cadeia não vira bug-fest.

Determinismo torna bug reproduzível

Quando a contabilidade falha, o caminho pra investigar é fixo: pegar seed + action log do bug report, replicar, navegar no tempo até o passo errado, ver qual sistema processou qual query com quais componentes. Sem determinismo, "às vezes acontece" é cemitério de bug.

Plano de refactor incremental — 4 fases

Visão de alto nível. O plano detalhado, com escopo passo a passo, contratos de código e critérios de aceitação, vive em migration_plan.md ao lado deste documento.

Fase 1 — Fundação (estado, determinismo, dados)

Action log explícito como sequência de comandos (Command Pattern materializado) · RNG seedado vivendo no game state · consolidação data-driven (todo conteúdo de jogo em um lugar, nada hardcoded fora dele) · máquina de estados das fases tornada explícita com transições validadas.

Fase 2 — Núcleo do engine (ECS, effects, events)

Modelagem do ECS world: entities como ids, componentes plugáveis uniformes (Health, Damage, Conditions, Modifiers, Triggers, Tokens) · sistemas que processam queries (damage system, heal system, draw system, etc.) substituindo handlers monolíticos · event bus interno síncrono com janelas pré/pós para cada operação de cálculo · stack de resolução pra efeitos encadeados. Esta fase é o coração: é aqui que a contabilidade passa a fechar.

Fase 3 — Fronteira e tecnologia

Projection layer explícita (selectors saem da interface, viram views nomeadas por consumidor) · engine adapter selando o core atrás de contrato uniforme · troca do store por substrato com integração nativa ao Redux DevTools, materializando o desejo de "estado observável".

Fase 4 — Persistência e tooling

Persistência por porta abstrata (snapshot + action log) com política "log é a verdade, snapshot é otimização" · replay viewer que rebobina partidas a partir do log · exportação JSON do log pra anexar em bug reports. Fecha o ciclo provando que a arquitetura cumpre a promessa.

O que fica explicitamente fora deste ciclo

Engine em outra thread (só se houver necessidade real de performance — o adapter já deixa a porta aberta) · servidor autoritativo e delta sync (incompatíveis com single-player; a disciplina das fases 1-2 já entrega o core portável caso um dia entrem) · content pipeline visual (ferramenta de produtividade pra autores, não engine).

Desejos (escolhas de tecnologia)

Separado de propósito: o desenho acima é tecnologicamente neutro. Esta seção lista preferências concretas que orientam como implementar as camadas, sem misturá-las à definição arquitetural — trocar uma escolha aqui não invalida o resto do documento.

Estado observável por Redux DevTools

O painel do Redux DevTools (extensão de navegador) é o critério prático de "estado bem desenhado": cada ação aparece nomeada, o diff de estado é legível, dá pra navegar no tempo e exportar o histórico. Qualquer store usado precisa expor essa integração — ela funciona como inspetor de ações, replay viewer rudimentar e arnês de debug, tudo no mesmo lugar, sem precisar construir devtools próprias.

Elf como substrato do store

Preferência por Elf como gerenciador de estado em vez de Redux clássico ou bibliotecas mais pesadas. Motivo: API mais simples e composicional, stores menores e independentes em vez de um único state root, e integração nativa com o painel do Redux DevTools — atende o desejo anterior sem o boilerplate. Encaixa bem no papel de adapter desta arquitetura: cada store é um ponto de entrada de comandos e uma fonte de projeção, sem virar o dono da lógica de regras (que continua no engine core).

Como esses desejos se encaixam nas camadas

O engine core permanece puro e ignorante de Elf — o store é cliente dele, não o contrário. O adapter é onde Elf entra: recebe comandos do consumidor, delega ao reducer do core, escreve o novo estado no store. O Redux DevTools observa o store do adapter, então cada ação visível no painel corresponde 1-pra-1 com uma entrada do action log autoritativo. Trocar Elf por outra biblioteca amanhã muda só essa camada.

Portabilidade pra backend Node (desejo de longo prazo)

A mesma disciplina que torna Elf trocável torna o engine portável pra um servidor Node com pouco esforço. Como o core é puro e ignorante do navegador, ele compila e roda em Node sem mudar uma linha — o mesmo arquivo que serve a interface local serve o servidor autoritativo. A migração troca apenas quem é dono de cada camada: action log e game state vivem no servidor; o cliente fica com Elf, Redux DevTools e a projeção que recebe pela rede. O adapter, que hoje é chamada de função, vira troca de mensagens — mesma assinatura, substrato diferente. Persistência migra de armazenamento local pra banco através da porta abstrata que já existe. O que custa de fato é o trabalho que qualquer backend multiplayer exigiria (sessão, autenticação, reconexão, anti-cheat) — não a reescrita do motor. Esse desejo não pede nada agora; só impõe uma restrição: manter comandos, eventos e estado puramente como dados serializáveis, sem closures nem objetos opacos.
