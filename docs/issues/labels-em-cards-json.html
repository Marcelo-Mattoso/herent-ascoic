Labels em cards.json — análise do problema

O campo label aparece como texto de display, mas funciona como contrato de comportamento — e diverge silenciosamente da implementação.

1. Como o problema apareceu

Durante a implementação do patch-10 (sistema de scripts) decidimos validar o subsistema migrando uma carta real. A escolha foi o Frasco de Óleo Incendiário: um item cuja label em cards.json dizia, em português claro:

"Brasa Viva (2/3): cause 2 de dano direto a uma criatura em jogo.
Se a criatura tiver a habilidade Corpo Gelatinoso, cause 3 de dano em vez de 2."

Inspecionando o handler genérico responsável (direct_damage) descobrimos que ele simplesmente faz parseNumber(value). Para value: "2/3" isso retorna null, e o handler sai cedo sem aplicar dano nenhum. A carta não fazia nada em jogo — havia anos, possivelmente — apesar de a label descrever em detalhe um comportamento condicional.

Essa lacuna é o que motivou esta análise. A label estava certa conceitualmente; a implementação estava ausente. E nada no sistema sinalizou que o texto da label não correspondia ao código.

Investigando mais, percebemos que esse não é um caso isolado: o campo label em cards.json tem uma natureza que entra em tensão com o resto da arquitetura.

2. Anatomia: o que é uma label hoje

Cada carta em cards.json que tem habilidade carrega um objeto Ability em um ou mais campos: skill, power, effect, purpleEffect. O objeto tem este formato:

{
  "skillId": "skill_living_ember",
  "name": "Brasa Viva",
  "value": "2/3",
  "type": "direct_damage",
  "trigger": "on_use",
  "target": "creature",
  "text": "cause 2 de dano direto a uma criatura em jogo. Se a criatura...",
  "label": "Brasa Viva (2/3): cause 2 de dano direto a uma criatura..."
}

Há 107 objetos Ability embutidos em cards.json, distribuídos assim:

A pergunta que nos interessa: quais desses subcampos são realmente lidos pelo runtime?

3. Três fontes de verdade para o mesmo comportamento

Hoje uma única habilidade — digamos, a Brasa Viva — existe simultaneamente em três lugares com naturezas diferentes:

FonteO que carregaQuem lêComo muda
cards.json
texto		 Label em linguagem natural, congelada com o valor já renderizado UI (4 componentes), exploration.ts em 2 pontos Manualmente, palavra por palavra
skills.json
tipo		 type, trigger, target, labelTemplate, usedBy[].value Engine inteiro (despacho de skill via type) Editando o catálogo central de skills
Handler / script
código		 Comportamento real em TypeScript: dano, condições, escolhas Engine, ao executar a skill Mudando código TS, com testes

Essas três fontes contam três histórias paralelas sobre a mesma habilidade. Nada no projeto garante que elas concordem. Quando divergem, vence quem o caminho de execução escolher consultar em cada momento:

  • Para despachar a skill em combate, o engine consulta skills.json: type decide qual handler roda.
  • Para mostrar o nome e a descrição ao jogador, a UI consulta cards.json: label é exibido cru.
  • Para fazer alguma coisa de fato acontecer, roda o handler ou o script: o comportamento real.

Resultado: o jogador lê uma promessa em cards.json, o engine despacha um type de skills.json, e o handler entrega o que o handler entrega. Os três podem estar contando coisas diferentes.

4. O que o código realmente lê de cards.json

Buscamos por todos os acessos a subcampos das Ability em cards.json, em todo o src/:

Em outras palavras: dos 8 subcampos de um Ability embutido em cards.json, somente label e name são consumidos pelo runtime. Os outros seis subcampos somam cerca de 70% do peso e são dados não lidos — embutidos no JSON, validados pelo carregador, tipados em cardTypes.ts, e nunca consultados.

Mas esses dados não lidos não estão inertes: eles divergem do skills.json, e essa divergência é uma pista sobre o que estava sendo planejado em outro momento do projeto.

5. Evidência: 45 de 87 labels divergem do template

Comparamos cada cards.json.label com o labelTemplate correspondente de skills.json, renderizado com o value que a carta declara. Critério: normalização de espaços em branco, igualdade exata do resto.

Mais da metade. As divergências têm padrões reconhecíveis:

  • A label de cards.json tem o valor entre parênteses no nome ("Juramento da Última Luz (5/5): ..."), o labelTemplate de skills.json não.
  • A label de cards.json adiciona prefixos como "uma vez por jogo, ..." que o template não tem (porque o template assume que o trigger já fala isso, mas o trigger não vai para a tela).
  • A label tem um número onde o template tem uma expressão (Fúria Rubra: ver §7).
  • Em ~25 casos a divergência é estrutural: type, trigger ou target não coincidem entre os dois arquivos (e o engine usa o de skills.json).

Nenhuma dessas divergências dispara alarme em build, lint ou teste. As duas fontes evoluíram em ritmos diferentes e ninguém as confronta.

6. Estudo de caso: Frasco de Óleo Incendiário

Este é o caso que nos chamou a atenção primeiro. Antes do patch-10, o estado das três fontes era:

cards.json — label

"Brasa Viva (2/3): cause 2 de dano direto a uma criatura em jogo. Se a criatura tiver a habilidade Corpo Gelatinoso, cause 3 de dano em vez de 2."

skills.json — type

"type": "direct_damage"   com valor "2/3" no usedBy do item.

handler direct_damage

parseNumber("2/3") retorna null. O handler tem guard if (!amount) return state. Resultado: nada acontece em jogo.

O que o jogador vê

Lê uma promessa detalhada com condicional. Usa o item. Não vê nenhuma mudança no inimigo. Sem feedback de erro.

A label encodava conhecimento que o handler genérico nem tentava avaliar: "se a criatura tiver Corpo Gelatinoso" é uma condicional sobre o estado de outra entidade. Nada em skills.json conseguia expressar isso, e o handler não foi feito para ler isso. A label era a única descrição correta do comportamento desejado — e era texto livre, não código.

Em outras palavras: o designer escreveu a especificação na label, esperando que o engine cumprisse. O engine cumpre uma parte (o número 2) e ignora o resto (a condicional).

7. Estudo de caso: Fúria Rubra

Um caso mais sutil, sem bug aparente, mas com divergência interna entre as três fontes.

cards.json — label (Bárbaro)

"Fúria Rubra (2): este personagem sofre 2 de dano para causar dano adicional igual a 6 no próximo ataque."

skills.json — labelTemplate

"Fúria Rubra ({value}): este personagem sofre {value} de dano para causar dano adicional igual a 3 vezes o valor sofrido no próximo ataque."

O value da skill é 2. Renderizando o template: "sofre 2 de dano para causar dano adicional igual a 3 vezes o valor sofrido". Em jogo, com value=2, isso seria 6 — coincide com a label.

Mas observe: a label de cards.json já materializou a multiplicação. Se um designer decidir balancear a Fúria Rubra mudando o value de 2 para 3 em skills.json (passando a infligir 9 de dano adicional), cards.json continuará dizendo "6", porque a label é um string congelado, não uma expressão calculada.

E há mais: o type de cards.json é "self_damage_for_damage" — um nome que descreve a lógica em palavras. O type de skills.json é "damage_bonus" — um handler genérico já existente. O engine despacha o segundo. O primeiro existe apenas como descrição em prosa do que se imaginava fazer, num passado em que provavelmente havia handler com aquele nome.

8. A mecânica da divergência

Por que essa configuração produz divergência inevitável?

8.1 A label não tem operação inversa

A label é texto livre escrito por humano. Não há algoritmo que extraia dela "trigger=on_use, target=creature_in_play, value=2/3, condicional Corpo Gelatinoso". Ela é o ponto final da informação — você pode chegar a ela rendererizando uma definição estruturada, mas não pode voltar dela para uma definição estruturada.

Por isso, qualquer mudança estrutural (no handler, no skills.json, no value) não consegue invalidar automaticamente a label correspondente em cards.json. A label é um snapshot que ninguém sabe se ainda está atualizado.

8.2 A label é especificação fantasma

Quando o designer escreve "Se a criatura tiver Corpo Gelatinoso, cause 3 de dano em vez de 2" na label, ele está descrevendo comportamento. Esse comportamento precisa estar em algum lugar do código para acontecer. Se não está, a label vira especificação fantasma: a expectativa do designer existe, mas o engine não tem como cumprir.

Como o sistema não distingue label que descreve de label que especifica, qualquer label nova pode estar prometendo comportamento que ninguém percebeu que precisava implementar. O Frasco de Óleo Incendiário viveu nesse estado.

8.3 O type embutido em cards.json é morto, mas mente

O type em cards.json não é lido pelo engine — verificamos. Mas ele existe, é validado, e tem nomes como self_damage_for_damage, fleeLock, controlProtection, recoverItem, targetRedirect, mark, damage, dice_adjust. Nenhum desses nomes corresponde a um handler real em src/core/skills/handlers/. São nomes históricos, vestígios de uma classificação que se transformou enquanto cards.json ficou parado.

Para quem lê cards.json tentando entender o que uma carta faz — designer, contribuidor novo, IA assistente — esses nomes parecem oficiais. Mas todos enganam.

8.4 A label não diz se o handler existe

Se o engine não tem handler para o type em skills.json, getHandler retorna null e dispara um console.warn: "[SKILL NÃO IMPLEMENTADA: ...]". É um sinal — fraco, mas existe.

Mas se o handler existe e cumpre parcialmente o que a label promete (como direct_damage com value "2/3", ou um handler que ignora uma condicional), nenhum sinal aparece. O sistema não tem como saber que a label promete mais do que o handler entrega, porque a label é texto livre.

9. Perguntas em aberto

Sem propor soluções, alguns recortes que ajudam a delimitar o que está em jogo:

  1. A label é display ou contrato? Hoje ela é tratada como display pela UI (texto cru exibido) e como contrato pelo designer (descrição autoritativa do que a carta deveria fazer). Esses dois papéis estão em tensão.
  2. Onde mora a descrição canônica do comportamento de uma habilidade? Possíveis respostas atuais: na label de cards.json, no labelTemplate de skills.json, no nome do type, no código do handler. Nenhuma resposta é completa, e cada uma é a "verdade" para uma audiência diferente.
  3. Por que a UI consome label de cards.json e não de skills.json? Histórico: skills.json chegou depois. Mas o resultado é que existem duas trilhas de descrição textual que tendem a divergir.
  4. Como saber se uma label nova promete comportamento não implementado? Hoje não há como, exceto leitura humana cruzando label, type e handler. O Frasco viveu silenciosamente quebrado por isso.
  5. O que aconteceria se cards.json não tivesse mais o objeto Ability? A UI perderia o acesso à label como string. Precisaria gerá-la a partir de outra fonte. Quem decide essa outra fonte? Quem garante que ela ainda comunica para o jogador o que a label de cards.json comunica hoje?
  6. Quando uma label de cards.json tem informação que skills.json não tem (condicional sobre Corpo Gelatinoso, escolha do jogador, comportamento alternativo), onde essa informação deveria viver?

Este documento intencionalmente não responde a essas perguntas. A intenção é registrar o problema como ele é, e que cada resposta passe por uma decisão deliberada — não por uma migração de campo de JSON.
